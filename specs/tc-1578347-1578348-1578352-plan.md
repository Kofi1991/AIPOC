## Drift found

- **TC-1578352 is blocked at the content-type level, not a UI-detail drift.** Live `/node/add` on test.registertovote.london only offers: Generic page, Homepage, Landing Page, News article / Blog post, Resource, Resource Collection. There is no "Project page" type to create, so none of its 4 steps (create with Image/media-lookup/Category-theme fields, Summary-not-displayed, Title-as-H1, Image-caption) can be exercised at all. **This will also block TC-1578350 (delete Project Page) and TC-1578351 (edit Project Page)** in the backlog — same root cause, worth raising with the team as one issue rather than three separate "automation gaps."
- **Rich text formatting (Bold/Underline/Link) cannot be reliably driven via keyboard shortcuts in this CKEditor5 build** — a `Ctrl+Shift+ArrowLeft` selection + `Ctrl+B`/`Ctrl+U` approach silently dropped/replaced typed text instead of formatting it. The editor exposes `window.Drupal.CKEditor5Instances`, and calling `.setData(html)` directly on the instance is the reliable mechanism — same one the editor itself uses to sync to the hidden form field. Confirmed live: `<strong>`, `<u>`, and `<a href>` all render correctly on the published page using this approach. New helper `contentPageHelper.setRichTextBody(page, html)` — it waits for `window.Drupal.CKEditor5Instances.size > 0` before calling `setData()`, since the instance isn't always registered yet immediately after the form loads (caught a real race condition running this spec back-to-back with another).
- **TC-1578348's edit flow redirects to `/admin/content` after Save & Close**, not to the node's own view page (the destination= query param on the Edit link controls this) — the case's "the changes will be reflected on the page" is verified via the content list row showing the new title and the "has been updated" message, not by visiting the node view page.
- **Site Admin steps (3-4) blocked pending credentials**, same as TC-1578345/1578346/1578349 — see those plans. `authHelper.login()` also still reuses `TC_ADMIN_SESSION` regardless of args passed, so this can't be worked around until either creds exist or that helper is extended.

## Test Scenarios

### 1. Generic Page Body Formatting

**Seed:** `tests/seed.spec.ts`

#### 1.1. Verify That Body Formatting Appears Correctly on the Front End for the Generic Content Page

**File:** `tests/smokeTest/verify-that-body-formatting-appears-correctly-on-the-front-end-for-the-generic-content-page.spec.js`

**Steps:**
1. Log in as Admin via `authHelper.login`
   - expect: authenticated session
2. Open the Generic page form, fill Title and Summary, then set the Body via `contentPageHelper.setRichTextBody(page, '<p><strong>Bold</strong> <u>Underline</u> <a href="https://example.com">Link</a></p>')`, then Save & Close
   - expect: page saves without error, navigates to its own view URL
3. On the view page, check the rendered body
   - expect: `<strong>` bold text, `<u>` underlined text, and the `<a href="https://example.com">` link are all present in the page HTML

### 2. Generic Page Editing

**Seed:** `tests/seed.spec.ts`

#### 2.1. Verify Users Are Able to Edit Newly Created Generic Content Pages. (Admin)

**File:** `tests/smokeTest/verify-users-are-able-to-edit-newly-created-generic-content-pages.spec.js`

**Steps:**
1. Log in as Admin, create a Generic page with a unique timestamped title (precondition)
   - expect: page created
2. Search the Content CMS list for that title and open its edit form via `contentPageHelper.editContentItemFromList(page, title)`
   - expect: edit form loads with the original title pre-filled
3. Change the Title to a new value and Save & Close
   - expect: browser lands on `/admin/content` with the message "Generic page \<new title\> has been updated."
4. Confirm the content list shows the new title and no longer shows the old one
   - expect: new-title row present, old-title-only row absent

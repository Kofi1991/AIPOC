## Drift found (verified live against test.registertovote.london, 2026-09-26)

- **TC-1578411's title ("manage content workflow") doesn't match its steps**, which are entirely
  about the site footer (logo, links, social buttons) and the Google Translate widget. Automated
  as written (the steps), not as titled.
- **Most of TC-1578411's static-presence checks are already covered** by TC-1601858 and
  TC-1601860 (footer logo/address/menu links/social icons all visible with correct `href`s) — but
  those specs only assert attributes, they never actually click through. This plan's spec adds the
  genuinely new coverage: clicking the footer logo lands on the homepage, three spot-checked
  footer links (Blog, How to vote, Resources) navigate to their real destinations, and the
  Facebook social icon opens the real external page in a new tab.
- **Google Translate's applied language does not appear instantly on a freshly-loaded page** —
  confirmed live: immediately after navigating to a second page, the title is still in English;
  the translation reapplies roughly 1-3 seconds later (observed via `<html lang>` and title
  changing after a wait, no `googtrans`-named cookie found to explain the mechanism directly).
  The spec waits for the title to change away from that page's own English title, with a 10s
  timeout, rather than asserting immediately after navigation.
- **`tests/helpers/translateHelper.js`'s `getLanguageSelect`/`getTranslateButton` are not
  exported** — only `expectTranslateWidgetVisible`, `pickRandomLanguage`, `translateAndVerify` are.
  Reverting to English reuses `translateAndVerify(page, 'English')` (the same retry-until-title-
  changes helper used for the initial translation), rather than driving the widget directly.
- **TC-1578411 step 9 (accessibility: hover/focus/tab/selected states)** is not automated, same
  reasoning as every other BBD case this session — the case's own author already spot-checked and
  waived a related issue elsewhere ("Focus box not seen on Translate button... treating as a pass
  for now").
- **TC-1578415's own account-creation form enforces password rules the case doesn't mention**:
  minimum 13 characters, at least 3 of {lowercase, uppercase, digit, special character}, and no
  two identical characters in a row. A password built from a timestamp (the usual pattern in this
  suite for unique values) tripped the last rule live, so the spec uses a fixed, hand-picked
  password meeting all three constraints instead of a timestamp-derived one — usernames stay
  timestamped for uniqueness, the password does not need to be.
- **The two password fields (`pass[pass1]`/`pass[pass2]`) must be filled with `pressSequentially`
  after a short settle wait, not `fill()` immediately on page load** — filling both instantly
  after navigation intermittently left the confirm field out of sync with the first ("the
  specified passwords do not match"), consistent with a client-side password-strength widget that
  attaches to the field shortly after load.
- **New Site Admin accounts are cleaned up via `/user/<uid>/cancel`**, choosing "Delete the
  account and its content" — this submits a Drupal batch job (redirects through `/batch?...`
  before landing back on `/admin/people`), so cleanup waits for the URL to leave `/batch` rather
  than checking for a status message immediately.
- Out of scope by standing convention: no mobile-viewport or visual-regression steps.
- TC-1578415 step 5 ("See original test plan for step details") has no actual content in
  TestCollab to automate — treated as the end of the case at step 4.

## Test Scenarios

### 1. Footer Navigation and Translate Persistence
**Seed:** `tests/seed.spec.ts`

#### 1.1 Verify user is able to manage content workflow
**TC:** 1578411 · **Priority:** High · **Tags:** role:fe-user, area:frontend
**Preconditions:** None — public pages, no login.

**Steps:**
1. Go to the homepage; get the footer (`footerHelper.getFooter`)
2. Click the footer's GLA logo
   - **Expect:** lands on the homepage
3. For each of "Blog", "How to vote", "Resources": go to the homepage, click that footer link
   - **Expect:** navigates to that link's real destination (`/blogs-and-news`, `/how-to-vote`, `/resources`)
4. Go to the homepage, click the Facebook social icon
   - **Expect:** opens `https://www.facebook.com/LDNgov` in a new tab
5. Pick a random non-English language from the translate widget (`translateHelper.pickRandomLanguage`) and translate (`translateAndVerify`)
   - **Expect:** page title changes away from English
6. Navigate to `/how-to-vote`
   - **Expect:** within 10s, the title changes away from "How to vote | Democracy Hub" (the translation reapplies)
7. Revert to English (`translateAndVerify(page, 'English')`)
   - **Expect:** title returns to "How to vote | Democracy Hub"

**Success criteria:** every navigation lands on its real destination; the translated language is still active on a second page (after the brief reapplication delay); reverting restores the English title.
**Failure conditions:** a footer link doesn't navigate, the Facebook popup doesn't open the real URL, or the translated language doesn't reapply within 10s on the second page.

### 2. Admin User Creation
**Seed:** `tests/seed.spec.ts`

#### 2.1 Verify that Admin user permissions work correctly
**TC:** 1578415 · **Priority:** High · **Tags:** role:admin, area:cms
**Preconditions:** Logged in as Admin (`authHelper.login`); the account has "Add user" access — verified live.

**Steps:**
1. Go to `/admin/people/create`; fill Email, a timestamped Username, and Password/Confirm password (fixed value meeting the site's complexity rules — see Drift); check the "Site admin" role
2. Click "Create new account"
   - **Expect:** "Created a new user account for `<username>`. No email has been sent." status message
3. Click the "People" breadcrumb/link
   - **Expect:** on `/admin/people`, a row for the new username is visible, status "Active"
4. Clean up: cancel the account via `/user/<uid>/cancel`, choosing "Delete the account and its content", wait for the batch redirect to clear

**Success criteria:** the account is created with the Site Admin role, appears in the People list, and is removed afterward so no test account is left on staging.
**Failure conditions:** a validation error on create (password policy, duplicate username), or the new user doesn't appear in the People list.
